🔐 Chữ ký số trên Báo cáo
EHC quản lý chữ ký số của nhân viên y tế theo quy định pháp luật. Khi in báo cáo sự cố, hệ thống sẽ tự động ký điện tử bởi các bên liên quan (người báo cáo, người xử lý, trưởng khoa, giám đốc).

➕ Bước 1: Tạo Sự cố
1
Nhân viên tạo sự cố trên Mobile App
iOS / Android App → BFF Gateway → Medical Incident Service
Người dùng điền form báo cáo sự cố (tiêu đề, mô tả, loại sự cố, mức độ nghiêm trọng, địa điểm, khoa phòng, thông tin bệnh nhân nếu có). App validate và gửi request lên BFF Gateway.
2
Backend lưu sự cố vào Database
PostgreSQL - medical_incidents table
MedicalIncidentService.CreateIncident() lưu thông tin vào database, tạo incident_id (SI-YYYY-NNNN), set status = REPORTED, lưu reporter info.
3
Tự động gọi API sang EHC để đồng bộ
HTTP POST → EHC API
Sau khi lưu thành công, backend tự động gọi EHC API để tạo bản ghi sự cố tương ứng. EHC sẽ gán EHC_INCIDENT_ID và trả về cho hệ thống để lưu vào medical_incidents.ehc_incident_id.
🔌 API Endpoint
POST /api/ehc/incidents/create

Loại sự cố (code)

Mức độ nghiêm trọng (LOW/MEDIUM/HIGH/CRITICAL)

ID nhân viên báo cáo

ID bệnh nhân liên quan (nếu có)

✅ Bước 2: Hoàn thành Sự cố & In Báo cáo
1
Cập nhật trạng thái → CLOSED
Người xử lý đánh dấu sự cố đã hoàn thành
Sau khi điều tra, xử lý, và phân tích xong (tab Phân tích TT43 Phụ lục IV đã hoàn thành), người có thẩm quyền cập nhật status = CLOSED với note cuối cùng.
2
Backend chuẩn bị dữ liệu đầy đủ
Aggregate toàn bộ thông tin sự cố
Hệ thống collect toàn bộ dữ liệu: thông tin cơ bản, lịch sử trạng thái, handling records, messages, phân tích TT43 (groups, causes, assessment), chữ ký cần thiết.
3
Gọi API EHC để báo kết thúc & yêu cầu in
HTTP POST → EHC API với đầy đủ payload
Backend gọi EHC API /incidents/complete với toàn bộ dữ liệu. EHC sẽ generate 2 báo cáo PDF (Phụ lục III và IV) với chữ ký số, lưu trữ và trả về URL download.
🔌 API Endpoint
POST /api/ehc/incidents/complete

4
Lưu URL báo cáo vào Database
medical_incidents table - report URLs
Backend lưu report_phu_luc_3_url và report_phu_luc_4_url vào database để người dùng có thể tải về bất cứ lúc nào từ app.
5
User tải báo cáo từ Mobile App
Download PDF với chữ ký số hợp lệ
Trên detail screen (tab Thông tin), hiển thị button "📄 Tải Báo cáo TT43". User click → app download PDF từ URL → mở bằng PDF viewer. File PDF đã có chữ ký số embedded, có thể verify bằng Adobe Reader.

⚙️ Technical Implementation Notes
💡 Backend Implementation
•
Sử dụng HttpClient with Polly retry policy khi gọi EHC API (retry 3 lần với exponential backoff)
•
EHC API call phải async/await để không block main thread
•
Nếu EHC API fail, lưu incident vào DB trước, sau đó retry background job (Hangfire)
•
Store ehc_incident_id vào medical_incidents table (indexed column)
•
Report URLs có expiration time → re-generate nếu user request sau 30 ngày
•
Authentication: Bearer token hoặc API Key trong header Authorization
•
Logging: Log toàn bộ request/response với EHC API (dùng Serilog structured logging)
📱 Mobile App Implementation
•
Tab "Thông tin" detail screen: thêm section "Báo cáo TT43" với 2 buttons download
•
Download PDF: sử dụng URLSession (iOS) / OkHttp (Android) → save to temp → open với system PDF viewer
•
Show progress indicator khi download (file có thể 500KB-2MB)
•
iOS: Present UIDocumentInteractionController hoặc Quick Look
•
Android: Intent với ACTION_VIEW cho PDF (Chrome, Adobe Reader, etc.)
•
Handle error: network timeout, file not found, expired URL
🔐 Security & Compliance
•
EHC API phải dùng HTTPS/TLS 1.3 bắt buộc
•
Chữ ký số tuân thủ Luật Giao dịch điện tử 51/2005/QH11
•
PDF signature: sử dụng PAdES (PDF Advanced Electronic Signatures) format
•
Timestamp Authority (TSA) để verify thời gian ký hợp lệ
•
Report URLs phải có signed token (không public direct link)
•
Audit log: Ghi nhận mọi lần download báo cáo (who, when, which report)
⚠️ Error Handling Scenarios
❌ Xử lý Lỗi
SCENARIO 1: EHC API Timeout khi tạo sự cố
→ Lưu incident vào DB với ehc_incident_id = null. Đánh dấu cần retry. Background job sẽ gọi lại EHC API sau 1 phút. User vẫn thấy incident được tạo thành công.
SCENARIO 2: EHC API trả về 400 Bad Request
→ Validation error từ EHC. Log chi tiết error response. Thông báo cho user "Không thể đồng bộ với EHC, vui lòng liên hệ IT". Incident vẫn được lưu, nhưng không có ehc_incident_id.
SCENARIO 3: Generate PDF thất bại (EHC 500 error)
→ Thông báo "Không thể tạo báo cáo lúc này, vui lòng thử lại sau". User có thể retry bằng button "Tạo lại Báo cáo". Backend gọi lại API /incidents/regenerate-reports.
SCENARIO 4: Report URL expired
→ Khi user download mà nhận 404/403, app tự động gọi API /incidents/{id}/refresh-reports. Backend gọi EHC API để re-generate URLs mới (PDF vẫn có trong storage).
SCENARIO 5: Thiếu dữ liệu bắt buộc khi complete
→ Validate trước khi cho phép CLOSED: phải có ít nhất 1 handling record, phân tích TT43 phải điền đủ các mục bắt buộc. Nếu thiếu, show error "Vui lòng hoàn thành Phân tích TT43 trước khi đóng sự cố".
✅ Tổng Kết

Quy trình tích hợp giữa Hệ thống Quản lý Sự cố Y khoa và EHC đảm bảo:

  • ✅ Đồng bộ tự động khi tạo/hoàn thành sự cố
  • ✅ In báo cáo chuẩn TT43/2018-BYT (Phụ lục III & IV)
  • ✅ Chữ ký số hợp lệ tuân thủ quy định pháp luật
  • ✅ Lưu trữ lâu dài với URL download cho người dùng
  • ✅ Retry mechanism đảm bảo không mất dữ liệu khi API fail
  • ✅ Audit trail đầy đủ cho mục đích kiểm toán

📌 Lưu ý: EHC System cần expose 3 endpoints chính: /incidents/create, /incidents/complete, và /incidents/regenerate-reports. Contract API cần thống nhất giữa 2 team trước khi implement.
